# SubHub core beliefs

这些信念指导所有架构决策。开发 Agent 在两个都合法的方案间犹豫时，回到这里找方向。
产品中的配置 Agent 与开发 Agent 是两种角色；#13 只约束开发协作。
配置原则以本文为唯一权威，其他文档引用对应编号；删除的编号不复用。标为“尚未实现”的约束是目标，不是现状。

## #0 元原则：按能力域定锚，跨端逐层投影

维护一份意图，投影到 Surge、Mihomo、Shadowrocket。意图是期望状态，生成配置是投影，客户端实测是观测状态；三者不得混为一谈。
调和必须以已批准意图为目标，不得因某端能力不足反改意图。

三端差异必须分清语法（怎么写）、语义（做什么）、能力（能否做到）、下发（如何送达生效）四层。
相似字段也可能造成不同流量行为；能统一的是意图，不是字段或文本。
每个 family 仍按已验证的语义和运行结果定锚，不按品牌排总序；低能力端不得削弱其他端。
不能等价表达时必须诊断并拒绝，或提出降级方案。降级方案可以先预览，经批准后才应用和下发；预览不得生效。不得静默跳过或伪模拟。

现有落点：`profile_capabilities.py`、`profile_editor_schema.py` 与 [family 审计](profile-single-source-review.md) 的 shared / adapted / blocked / standalone 分类。
[派生意图模型与兼容投影](configuration-intent.md) 已实现，只保留原输出并增加管理诊断；降级批准尚未实现，现有告警、跳过不等于完整满足本原则。

## #1 边界处翻译与守门，内部只说一种语言

Agent 提案与订阅源、人工导入一样，都是边界输入，不能因提出者可信就直接生效。
所有输入必须经过 schema 校验和规范化；配置提案还必须经过能力门控、预览和批准。
预览不得写入生效配置，必须与应用执行相同的权限和有效性检查，展示意图差异、三端行为变化、风险和证据。
内部只接受已校验的统一表示，不得二次猜测。批准与快照绑定见 #14。

现有落点：节点转为 `NodeRecord`；工作流 export → preview-import → apply；`subhub.patch.v1` 的校验与预览。
现有预览尚未覆盖全部配置和三端行为、风险、证据；统一能力门控与批准链尚未实现。
管理端前端读取的每个响应都经 `frontend/src/api/validators/` 运行时校验，字段缺失直接报错、不补默认值；`apiGet` 必须带 parser，写操作不带 parser 时返回值只能是 `unknown`。

## #2 节点质量分层治理是本项目存在的前提

节点必须按质量分层，层与层之间严格隔离。
如果放弃分层——允许混用、允许降级——这个软件就失去了存在的理由。
所有具体的隔离规则（空池终止、禁止跨梯队借节点）都从这条信念派生。
所有面向用户暴露的契约语义，都必须建立在清晰的质量边界之上；语义可以调整，边界不能含混。

## #3 用户对生效中的路由语义拥有完全的可见性和控制权

Agent 是主要配置者；人是读者、审批者和微调者。控制权不以人逐字段维护为前提。
用户必须能查看当前生效意图、契约、默认去向和规则命中结果，并能审阅、否决和微调提案。
不得存在用户无法查看或修改的隐藏契约语义，否则自动配置只会把失控藏得更深。

预置契约仍只是初始化模板。稳定标识保证改名不破坏引用；删除后不得自动重建。
合并和默认去向迁移必须显式指定，按 #4、#14 生效；直连、拒绝不依赖永久保留的预置 ID。

现有落点：契约生命周期管理、`route_contract_views.py` 和设备预览。
Agent 主配置的完整流程尚未实现；现有表单保留微调能力，不代表用户必须逐项填写。

## #4 分流语义必须显式声明，系统不做推断

节点质量、规则归属、契约名称和契约意图等分流语义，必须由人或 Agent 显式声明，以批准为生效依据。
声明者可以改变，显式性不能改变；Agent 可提出有依据的分类建议，系统不得把建议直接当成生效事实。

系统不得根据旧名字、展示位置、池成员或历史默认值猜测名称、合并目标和意图。
现有落点：显式 `routing_action`、规则目标与契约引用迁移校验。全局批准强制执行尚未实现，约束见 #14。

## #5 系统永远不隐瞒问题

拉取失败、能力缺失、渲染降级和空池都必须透明报告，不能用成功状态或 fallback 掩盖。
每条诊断必须同时提供稳定代码和白话说明：代码供 Agent 与脚本判断，说明讲实际后果，并给出可执行的处理办法。
不得让脚本解析会翻译或改写的说明文字来判断错误类型。

现有落点：patch 的 `blockers/warnings`、Profile 能力诊断与设备预览诊断；来源页拉取失败但仍在用缓存节点时标琥珀，没有节点可用时标红，并逐端列出原因（`sourceHealth.ts`、`ReasonTable`）；标准源拉取失败带 `last_pull_reasons`，每项是稳定代码加白话说明，来源页按代码取文案。
全量诊断的稳定代码与白话说明尚未实现；旧工作流仍有纯文本错误，core 诊断的 `status` 仍按 `last_pull_error` 里的关键词推断，不能宣称全量达标。

## #6 展示组织与流量语义必须分离

展示层的分组、排序、命名，是为了帮助人理解和管理；
流量命中后的去向，是另一层独立语义。

两者可以关联，但不能互相推导。
系统不能从展示组织反推流量语义，也不能把底层资源结构直接当作用户面对的契约语义。

## #8 地图与手册必须分层

`AGENTS.md` 的职责是地图：告诉人和 agent 去哪里找真相。
runbook 的职责是手册：告诉人和 agent 到了那里之后应该按什么顺序做事。

地图不能膨胀成全文手册；手册也不能退化成一堆入口链接。
两者混在一起，仓库就会重新滑回“读了很多，但还是不知道下一步怎么做”。

## #13 人类掌舵，Agent 执行

本条只讲写代码的开发 Agent：人类负责目标、原则、边界、验收和门禁设计；
开发 Agent 负责实现、验证、反馈消费和修复推进。

人类不必亲写每行代码，但开发执行必须服从仓库内的可执行约束。
产品中写配置的 Agent 按 #3 分工、按 #1 进入系统、按 #14 获得批准；不得用本条代替产品审批规则。

## #14 批准按风险分级，并锁定预览快照

Agent 只能代批纯管理元数据，即不进入订阅输出、LLM 输入或分组模式的变更，例如管理视图排序、纯备注。
规则、质量分类、契约目标、来源与节点、DNS、MITM、TUN、凭据和安全变更必须由人批准。
风险等级由服务端按实际差异与影响核对并留审计，不得信任提案自报；混合变更取最高等级，无法证明无影响时交人批准。
服务端门控实现前，不得开放 Agent 代批。

批准必须绑定预览的基线快照、提案和投影依据，应用时重新核对；任一变化都必须拒绝并重新预览、批准，不得沿用旧批准。
否则用户批准的内容与真正生效的内容可能不同。

现有落点：工作流 snapshot fingerprint、漂移 409、directness 接受后锁定；通用 patch 的 `base_revision` 检查。
这些只覆盖局部状态；服务端分级、不可变批准记录和完整快照锁定尚未实现。

## #15 每次生效必须可追溯、可回滚

每次生效必须记录提出者（人或具体 Agent）、批准者、时间、依据、差异和所批准快照。
系统必须能回到任一已批准快照；恢复仍须遵守 #1、#14，不得用回滚绕过批准或能力检查。
只有知道谁改了什么、为什么改、如何恢复，自动配置才可长期托付。

现有落点：策略备份的版本快照、恢复预览、digest 核对和恢复结果。
全量变更身份链、每次批准的快照留存与任一已批准快照回滚尚未实现；备份版本不等于批准记录。

## #16 渲染与下发必须确定

同一份已批准意图、同一份节点数据、同一版本，输出必须逐字节相同。
规则内容、目标客户端、设备和下发上下文必须作为输入固定，不能靠未记录的环境补齐。
LLM 不得进入渲染或订阅下发路径；当前时间、随机数也不得暗中改变输出。否则预览无法复现，批准便失去依据。

现有落点：`build_policy_ir()`、各端渲染器与订阅缓存；LLM 工作流在边界外产生提案。
[意图兼容投影](configuration-intent.md) 冻结设置/分流输入并测试逐字节复现；离线包时间和地址观测由边界显式传入，但签名资产 URL 的 exp 仍是渲染过程中唯一读取时钟的输入，这是基线既有行为；冻结该时钟才能复现真实下发。完整批准快照与运行端调和仍未实现。

## #17 解释必须讲行为，界面靠布局说话

给人看的解释必须描述配置后果，例如“这类流量在 Surge 被拒绝，在 Shadowrocket 直连”。
必须区分生成配置的预期行为与已验证的运行行为，证据不足时明确说明；人主要阅读和批准之后，更需要这些依据。
不得用“点击这里再保存”等界面教学替代行为解释；不得堆叠不必要的二级标签或描述。操作关系应由布局表达，可访问名称和必要错误指引仍须保留。

现有落点：core explain、Profile 投影预览和设备诊断；管理端按 [DESIGN.md](../../DESIGN.md) 用一个点加一句短语报告状态，同一状态只在一处说，页头说明只留给流程不自明的页面。
统一行为解释尚未实现；现有教学文字仍需后续清理。
